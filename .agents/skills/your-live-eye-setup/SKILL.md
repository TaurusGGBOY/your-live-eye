# 你的眼：初始化与部署

本 Skill 随仓库提供，无需用户自行创建。先定位包含 `pyproject.toml` 的项目根目录，读取 [README](../../../README.md)；部署时读取 [部署说明](../../../docs/deployment.md)。不要使用旧聊天中的绝对目录、账号或主播作为新用户的配置。

## 确认实际选择

先复用本次用户已经明确的选择和当前 `config.json`，只问缺失或矛盾的信息，合并成简短问题；不重复要求确认已授权动作。

| 项目 | 应确认的内容 | 建议值与处理 |
| --- | --- | --- |
| 直播间 | UID、昵称或主页/直播间链接；解析出的昵称、UID、房间号 | 先运行 `resolve` 核对身份；同名时请用户选 UID，不猜。没有目标时先问，不自行选明前奶绿。 |
| 初始化模式 | 正式使用，还是明确要轻量 Demo | 正式默认 `--date all`，抓取来源中全部已结束历史；只有用户明确选 Demo 才用 `--demo` 或指定日期。明前奶绿是可选示例，不是默认目标。 |
| 模型与状态 | 本机 Codex 登录，或云端兼容 API；持久目录或私有 R2 桶 | 本机默认 Luna high/Fast；GitHub 托管模式需选该 API 实际可用的模型，不把 CLI 模型名当 API 权限。全历史先报告目录场次/日期范围，不把单日耗时当全部工期。 |
| 部署 | 本机/LAN、Cloudflare Pages，或两者 | Cloudflare 需要用户自己的 Account ID、Pages 项目名、生产分支、Token 的保存位置及是否启用自动发布。只确认配置是否存在，不要求把 Token 粘贴到聊天。Kafka 是另一个产品；不把口误变成消息队列依赖。 |
| 每日更新 | 是否启用、当地时间、时区、成功后是否发布 Cloudflare | 建议每天 `04:00 Asia/Shanghai`；补齐未完成/失败/迟到档案及新 Message/SC。选择 Cloudflare 定时发布时使用项目 Action。 |

把选择简明复述给用户；有未决身份、模式或发布目标时先保存可审阅配置，继续准备安装，暂不执行依赖该选择的下载/发布。用户已给出明确选择时直接执行，不额外加一道确认。

## 开始前给出耗时预估

在完整初始化前先读来源目录，说明可用场次、起止日期、来源报告消息量和已有完成量，区分首次全历史与每日增量。不要把“最近一天”默认为首次全历史工作量，也不要把来源总消息量当已解码的弹幕/SC 或去重原文数。

以相同模型、思考强度、并发和批量的实际记录估算；没有可比记录时，在用户已选定的范围与模型内先测一小批，再给全量预计时间。小批测量先说明用途与大致耗时，成功结果继续复用。没有可用模型时说明尚缺实测、给出完成估算所需的一步，不编造精确 ETA。

估算分别考虑下载、初判、独立强度评分、玩梗语义审核和部署。使用完成的真实工作量除以墙钟吞吐，不把并发 worker 时长之和或“全部复用缓存的恢复耗时”当全量速度；争吵比例、玩梗候选数量、同文复用比例和模型限流会影响范围。输出有上下界的规划范围，注明样本量、参数和主要不确定性。模型未确定时先给有依据的场景估算，选择后更新。

在开始大批运行前，向用户给出：

> 本次处理：〈主播、模式、日期范围、预计消息量〉。按〈实测样本与参数〉，预计总耗时〈范围〉；页面预计在〈分类及对账完成后，所需时间范围〉可用。已有页面继续展示上次成功结果。可能延长的因素：〈本次实际因素〉。运行中每 5 分钟更新完成量、耗时和剩余时间。

运行期间读取 `progress.json`、`coverage.json` 与 `last-run.json`，按真实已完成量每 5 分钟给进度和修订 ETA。刚开始尚不足以外推时如实说明。区分下载完成、模型完成、页面发布；失败/限流停滞时立即告知原因和已保留进度。最终交付列出**预计时间与实际墙钟时间**，不能把子任务耗时相加充当实际墙钟。

先读[实测耗时](../../../docs/runtime-estimates.md)：火之眼267万事件主分类3小时22分、53,079种纯评分约16分钟；两段相加不是首次初始化墙钟。全历史玩梗审核没有端到端实测，需单列估时，不能据主分类速度承诺整套4小时。默认玩梗沿用用户选定的模型；可显式用 `--meme-model` / `--meme-reasoning` 选择，不能静默替换。

## 按配置执行

- 正式本机：`./run.sh run "用户输入" --date all --update-at 04:00 --timezone Asia/Shanghai --deploy --schedule`。
- 轻量 Demo：仅在已选择后加 `--demo`（默认最近已结束场次），或 `--date YYYY-MM-DD`。指定日缺档不得悄悄换日；用户允许最近场次才加 `--fallback-latest`。
- Cloudflare：默认 GitHub 托管 `ubuntu-latest`，无需用户安装 runner。先 `resolve` 确认 UID，按部署文档设置 UID、API 模型、私有 R2 状态桶、Pages 项目及 Variables/Secrets，再运行 Action 的 `update`。正式范围默认 `all`；明确选择 Demo 才设 `latest` 或日期。R2 必须关闭公开访问；状态不能放公开仓库、Actions cache 或 artifact。
- 用户已有常驻主机时可选 `YOUR_LIVE_EYE_RUNNER=self-hosted`，先 `./run.sh run "用户输入" --date all --configure-only` 保存配置，设置 `YOUR_LIVE_EYE_CONFIG` 和 `your-live-eye` runner 标签。不能因为项目作者自托管，就要求所有用户自托管。两种模式 `update` 均初始化/补齐并发布，`publish` 只导出已成功数据。
- 估时包括云端恢复/保存状态的开销；GitHub 托管单次处理窗口约 4.5 小时，超出后分次恢复。免费 runner 不代表模型 API 或 R2 无限免费，不虚报整套零费用。展示首次页面预计时间与跨多次任务的全量时间。
- 选定其他更新时间/时区时，同时设置 `--update-at` / `--timezone`，并修改 Action 的 cron 对应 UTC 时间。读回两者，明确展示用户当地时间和时区；只改文档不算配置完成。
- Cloudflare 日更开启后，不再为同一数据集安装第二套本机日更；本机页面服务可以独立保留。已有本机调度先查状态，切换时只移除该配置的旧定时器。
- `config.json` 放在独立状态目录。只保存非凭据选择；Token/模型密钥由用户放入 Secrets 或其密钥管理环境，仓库仅包含变量名。不得沿用原 Hinome 云账号。
- 已有数据用 `resume --config ...`；失败补跑用 `--retry-failed`，保留成功结果和原始回执。由 Demo 转正式时先保留旧配置，再把同一配置的 `date` 改为 `all` 后恢复，不重新建库重复花费。当前用户明确保留轻量 Demo 时不得自动扩成全历史。

版本升级复用既有结果，新原文使用争吵提示、评分默认2048条/批且只给强度。旧未完成初判按冻结提示接续，旧二次改类阶段停用并保留回执。每日流程同时审核新增/变化玩梗材料，检查 `memes/progress.json`；没有确切证据不凑话题。旧日只有原文频次时须标明尚未语义审核。可用 `review-memes --config ...` 单独补审核而不重新分类；该命令不自动发布，完成后重建部署。

## 验收与交付

检查 `coverage.json`、`last-run.json` 和 `status`：正式模式应覆盖来源目录中全部可处理场次；仍在播、档案未收录、下载失败和模型未决分别说明。不能用“所有来源中已收录日”冒充真实全部直播日。

打开实际页面核对主播、日期列表、总数、分数与五分钟下钻；Cloudflare 已发布需打开 Action 返回的 URL，不能仅凭文件存在或上传命令成功称已上线。日更读回时间/时区与持久状态；执行失败不得推进成功日期。首次和日更使用同一处理流程。

最终给出配置文件位置、模式/覆盖范围、访问网址、更新时间/时区、发布方式和未完成步骤。需要用户配置账号或 runner 时，说明具体缺项并交付已完成的文件，不声称已在 GitHub/Cloudflare 实跑。
